# 6차 보고서: 시험 풀이 어댑터 학습 + 전문가 캐싱 서빙 최적화

작성: 2026-11-24
환경: RTX 3070 8GB / RAM 16GB / Ryzen 5 5600X
모델: Qwen3.6-35B-A3B IQ3_S

## 0. 결론

1. **시험 어댑터(c1a)**
   - 학습에 쓰지 않은 2027학년도 문제에서 단계별 풀이 정답률이 **24.2% → 52.5%**로 올랐습니다.
   - 사고 모드를 켠 원래 모델(48.3%, 문항당 약 2,970토큰)과 비슷하거나 약간 높은 수준을, 3분의 1 이하의 토큰으로 냅니다.
   - 대신 바로 답하기(−6%p)와 일반 상식(HAE-RAE −4%p)은 떨어졌습니다. 그래서 **객관식 시험 문제에만 자동으로 켜지도록** 채팅 앱에 넣었습니다.
2. **전문가 캐싱**: 엔진에 들어 있는 GPU 전문가 캐시를 이 PC에 맞게 조정해서 생성 속도가 **초당 38토큰 → 59~60토큰(+55%)**으로 올랐습니다.
   - 정답률 변화는 없습니다(925문항 기준 62.7% → 62.6%, 1문항 차이).
   - GPU 메모리가 시스템 RAM으로 넘치는 현상도 없습니다.

## 1. 학습 데이터 (비공개, 이 저장소에 포함하지 않음)

- 약 2,900개의 비공개 한국어 단계별 풀이. 풀이 형식: 공식 단계 / 오답 소거 / 단서 우선 / 사고 모드 형식
- 1차 학습 묶음(chunk 0): 448개 시퀀스, 22만 토큰.
- 평가는 2027학년도 문제만 썼고, 학습이나 검색 자료에는 넣지 않았습니다. 한국어 벤치마크(HAE-RAE, KMMLU, 공무원, 2025 수능 국어, 925문항)도 평가에만 썼습니다.

## 2. 학습 과정에서 해결한 문제

| 문제 | 해결 |
|---|---|
| 일부 시험 문항이 4천 토큰에 가까워 기록 도구 한계(2,048토큰)를 넘음 | 1,500토큰 이하 문항만 평가에 사용 |
| GPU 메모리 부족, 시스템 RAM으로 넘쳐 1회차 학습이 1시간 이상 걸림 | 토큰 수 기준 배치, 전문가 출력을 반정밀도로 보관 |
| 선형 어텐션(DeltaNet)을 토큰 하나씩 계산해서 매우 느림 | 64토큰 묶음 계산(WY 변환)으로 교체. 결과는 오차 1e-6 이내로 같고(기울기 포함), **약 40배 빨라짐**(1회차 학습 3.6시간 → 7분) |
| 일상 문장 이탈: c0는 87.8%로 기준(92%) 미달 | 일상 문장 보호 가중치 4 → 12, 길이 64 → 128, 학습률 낮춤 → c1a **93.2%** |

**해석**
- 단계별 풀이 점수가 오른 데에는 풀이를 끝까지 마치고 정답 줄로 끝맺는 습관이 크게 작용했습니다.
- 60문항에서 3문항 차이라, 추론력 자체가 확실히 올랐다고 말하기에는 통계적으로 부족합니다.
- 정직하게 말할 수 있는 결론은 "같은 정확도의 답을 훨씬 짧고 빠르게 낸다"입니다.

## 4. 전문가 캐싱 서빙 최적화 (`scripts/serve/bench_serve.py`, `results/serve_bench.jsonl`)

| 설정 | 생성 속도 (256토큰) | 1,024토큰 생성 | VRAM |
|---|---|---|---|
| 이전: 층 26개 CPU, 캐시 없음 | 38.0 | 35.9 | 7.0GB |
| KV 8비트 + 층 22개 CPU | 44.4 | — | 7.7GB |
| 층 32개 CPU + 캐시 2200MiB, CPU 분담 100% | 45.8 | — | 7.6GB |
| **층 32개 CPU + 캐시 2000~2200MiB, CPU 분담 80%** | **59.4~59.5** | **53.4** | 7.6GB |
| 위 설정 + 시험 어댑터 | — | 57.2 | 7.6GB |
| 전부 CPU + 캐시 4400MiB, KV 8비트 | 58.6 | — | 7.2GB |

- 캐시에 없는 전문가 중 20%는 GPU로 올려서 캐시가 계속 학습되게 하고, 80%는 CPU가 계산하게 했을 때가 가장 빨랐습니다. CPU 분담 70~90%는 측정상 같았습니다.
  - 100%로 하면 캐시가 처음 채워진 상태로 굳어 느려집니다.
  - "자주 쓰는 부위만 미리 올려두는" 아이디어를 자동으로 학습하며 하는 방식입니다.
- 스레드 수, 프로세스 우선순위, 폴링 설정은 차이가 없었습니다.
- 배치 2048은 긴 문서 처리가 1,163 → 1,498토큰/초로 빨라지지만 VRAM이 7.9GB로 한계라서 쓰지 않았습니다.
- 채팅 앱 실측(프록시 경유): 일반 질문 초당 61토큰, 시험 문제 초당 62토큰(5초 안에 정답).

## 5. 검토했지만 적용하지 않은 것

- **엔진 코드 수정(`llama.dll` 재빌드)**
  - 공식 서버의 보조 DLL이 MSVC 방식의 C++ 함수를 `llama.dll`에서 가져다 씁니다.
  - 그래서 MSVC/Windows SDK를 시스템에 설치하지 않고는 호환되는 DLL을 만들 수 없습니다. 컴퓨터 안전 원칙에 따라 하지 않았습니다.
  - 대상이었던 개선 두 가지:
    - 공용 전문가를 CPU 전문가 계산과 동시에 돌리기
    - 다음 층 전문가를 예측해서 미리 올리기
  - 예상 효과는 5~10% 정도입니다.
- **확산 모델 초안(추측 디코딩)**
  - 이 PC처럼 전문가를 RAM에 두는 구조에서는 초안 토큰을 검증할 때 읽을 전문가가 늘어나 손해입니다.
  - MTP 추측 디코딩도 실측에서 더 느렸습니다.
- **SSD 선행 로딩**
  - 지금 모델(12.7GB)은 RAM에 들어가서 이득이 작습니다.
  - 더 좋은 4비트 파일(17GB, RAM 초과)을 쓸 때의 과제로 남겨 둡니다.
